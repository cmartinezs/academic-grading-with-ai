# ADR-0008 — Portal autenticado o estático con contenido cifrado

- Estado: Aprobado
- Fecha: 2026-08-01
- Fecha de aprobación: 2026-08-01
- Reemplaza: fragmentos protegidos solo por access code PBKDF2

## Contexto

Un hosting estático no ofrece rate limiting ni autorización por estudiante. PBKDF2 no
protege datos publicados en texto plano y un código corto puede probarse offline después
de descargar el archivo. HTTPS protege el tránsito, no controla quién puede leer un objeto.

## Decisión

El portal soporta dos modos explícitos.

### Modo A — Hosting autenticado

Preferido cuando exista infraestructura con identidad y autorización real. El hosting debe
garantizar que un estudiante solo pueda obtener su proyección.

### Modo B — Hosting estático cifrado

- Una proyección por estudiante.
- Payload cifrado con AES-GCM.
- Clave de contenido aleatoria de alta entropía.
- Object ID aleatorio y no enumerable.
- Capability URL cuya clave viaja en el fragmento `#`; el fragmento no se envía al servidor.
- Sin dataset global servible.
- CSP estricta, `noindex`, policy de cache y referrer control.
- Rotación por `publicationId`.

La capability es un bearer secret. Debe tener al menos 128 bits de entropía efectiva. No
se aceptan RUT, fechas, PINs cortos o códigos memorizables como base de seguridad.

PBKDF2 puede usarse únicamente como función derivadora documentada para un secreto ya de
alta entropía o como capa UX adicional; no compensa baja entropía. Sus parámetros se
registran junto al blob y no se fijan como garantía arquitectónica eterna.

`publish`, `revoke` y `purge` son ejecutores con receipts. La documentación declara que
revocar no elimina copias descargadas ni garantiza purga inmediata de todas las caches.

## Alternativas consideradas

### Datos plaintext + validación JavaScript

Rechazada: el usuario puede leer el archivo directamente.

### Access code corto + PBKDF2

Rechazada: vulnerable a ataque offline.

### URL difícil de adivinar sin cifrado

Rechazada: una fuga del objeto expone plaintext.

### Hosting autenticado o blob cifrado

Aceptada.

## Consecuencias

- El portal requiere Web Crypto o una implementación criptográfica revisada.
- Las claves no se guardan en logs ni receipts.
- El pipeline de email puede entregar la capability, pero el portal no depende del email.
- Un link comprometido expone una proyección, no el dataset completo.
- El threat model y checklist de hosting son gates de C4.
