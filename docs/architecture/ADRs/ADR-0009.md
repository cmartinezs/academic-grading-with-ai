# ADR-0009 — Email en dos fases con aprobación por hash y ledger durable

- Estado: Propuesto
- Fecha: 2026-08-01

## Contexto

El envío SMTP es irreversible y puede fallar parcialmente. Un archivo de estado dentro de
`exports/` puede perderse, regenerarse o sufrir carreras. Una ventana temporal de siete
días tampoco representa idempotencia semántica y puede bloquear correcciones legítimas.

## Decisión

El flujo se divide en dos fases.

## Fase 1 — Prepare

Genera un plan inmutable con:

- `sectionId`;
- `publicationId`;
- destinatarios resueltos desde el roster privado;
- template e intent versionados;
- subject/body exactos;
- previews;
- conteos;
- `previewHash` sobre el payload efectivo.

Dry-run es el comportamiento por defecto.

## Fase 2 — Approve and execute

El docente aprueba el `previewHash`. Antes de enviar, el executor verifica que el plan no
cambió, adquiere un lock y consulta un ledger durable.

Clave idempotente mínima:

```text
sectionId + publicationId + studentId + recipient + templateVersion + intent
```

El ledger vive en estado operacional privado, no en un export regenerable. Usa escrituras
atómicas y locking. Registra intento, estado, timestamp, provider message ID y error
clasificado, sin cuerpo ni PII completa.

## Taxonomía de errores

- Template/schema inválido: fail-fast antes del primer envío.
- Autenticación/configuración SMTP: detener batch.
- Rate limit/conexión global: pausar batch y reanudar con control.
- Dirección inválida: marcar destinatario y continuar.
- Error individual transitorio: reintentar con backoff limitado.
- Estado ambiguo después de timeout: no reenviar automáticamente; requiere reconciliación.

`--force` no omite controles de forma global. Debe crear una intención nueva o una
excepción explícita, auditada y por destinatario.

## Alternativas consideradas

### Estado por batch en `exports/`

Rechazada: no es durable ni seguro ante regeneración/concurrencia.

### Ventana de siete días

Rechazada: heurística sin identidad de publicación/intención.

### Prepare/approve/execute + ledger

Aceptada.

## Consecuencias

- Cambiar destinatarios, template o contenido invalida la aprobación.
- El proceso es reanudable después de un fallo o reinicio.
- No se promete "cero envíos accidentales"; se busca prevenir, detectar y contener errores.
- Un email enviado no tiene rollback. Se definen acciones compensatorias y runbooks.
- El ledger requiere política de backup, retención y recuperación.
