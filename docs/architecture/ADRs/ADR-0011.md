# ADR-0011 — Lifecycle, provenance y correcciones de publicación

- Estado: Aprobado
- Fecha: 2026-08-01
- Fecha de aprobación: 2026-08-01

## Contexto

Portal, email, BI y auditoría necesitan una identidad común de publicación. Sin lifecycle,
una corrección puede sobrescribir resultados previos, un email puede quedar desligado del
contenido aprobado y una revocación puede confundirse con rollback.

## Decisión

Cada Publication Snapshot tiene un `publicationId` inmutable y un estado académico
explícito.

Estados mínimos:

```text
draft → reviewed → approved → published
                         ├──▶ superseded
                         ├──▶ corrected
                         └──▶ revoked
```

### Semántica

- `draft`: build no aprobado; puede regenerarse.
- `reviewed`: validaciones técnicas y revisión docente completadas.
- `approved`: contenido congelado y autorizado para publishers.
- `published`: al menos una proyección fue ejecutada/publicada con receipt.
- `superseded`: una publicación posterior la reemplaza sin afirmar error.
- `corrected`: una publicación posterior corrige un defecto y la referencia explícitamente.
- `revoked`: se ordenó retirar accesos/distribución; no implica borrar copias ya entregadas.

Un snapshot `approved` o posterior no se modifica. Toda corrección produce un nuevo
`publicationId` y declara:

- `supersedesPublicationId` o `correctsPublicationId`;
- motivo;
- campos afectados;
- aprobador;
- fecha;
- acciones compensatorias requeridas.

## Provenance obligatoria

El manifest registra:

- hashes de entradas;
- schema versions;
- parser/engine version;
- grade policy completa y hash;
- migrations aplicadas;
- creator/reviewer/approver mediante IDs auditables;
- clock/metadata de build;
- environment fingerprint relevante, sin secretos.

Cada operación externa genera un receipt ligado a `publicationId`:

- portal deployment ID/URL sin capability secret;
- email batch/intent IDs;
- BI release ID;
- revoke/purge outcome.

## Aprobaciones

La aprobación académica del snapshot es distinta de:

- aprobación de un batch de email;
- autorización de publicación del portal;
- aprobación de un release BI.

Cada operación verifica que el snapshot siga aprobado y que su payload coincida con el
hash revisado.

## Alternativas consideradas

### Sobrescribir el último export

Rechazada: destruye historial y provenance.

### Versionar solo por timestamp

Rechazada: no expresa relaciones de corrección ni aprobación.

### Lifecycle explícito

Aceptada.

## Consecuencias

- Email, portal y BI comparten una referencia académica común.
- Se conserva historial reproducible.
- Revocación y corrección se modelan como acciones/relaciones, no como rollback falso.
- Se requieren comandos y validadores de transición de estado.
- Los estados deben almacenarse de forma atómica y auditable.
