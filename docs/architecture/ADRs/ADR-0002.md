# ADR-0002 — Configuración estructural separada de la política de cálculo

- Estado: Aprobado
- Fecha: 2026-08-01
- Fecha de aprobación: 2026-08-01

## Contexto

El base ya genera `evaluations/<SECTION>/config.json`. El diseño anterior proponía
enriquecerlo con forms, pesos, fechas, tipos y acceso, mientras `grade-rules.json` y
`defaults.json` también podían contener ponderaciones. Esa duplicación crea múltiples
fuentes de autoridad.

## Decisión

Separar responsabilidades:

### `section-config.json`

Define estructura y metadata:

- curso/sección/periodo;
- evaluaciones y tipos;
- forms/variantes;
- fechas;
- referencias a rúbricas;
- referencia a `grade-policy`;
- configuración no secreta de publicación.

### `grade-policy.json`

Es la única autoridad para:

- ponderaciones;
- escala;
- faltantes;
- ajustes y bonos;
- reemplazos;
- caps/floors;
- redondeo;
- cálculo final.

### Defaults

Se usan exclusivamente para inicializar nuevos archivos. Antes de publicar, todo default
efectivo se materializa en la config o policy capturada por el snapshot.

Ambos contratos declaran `schemaVersion` y se validan por separado.

## Alternativas consideradas

### Todo en `config.json`

Rechazada: mezcla metadata, seguridad, estructura y cálculo; dificulta versionar policies.

### Pesos duplicados con precedencia

Rechazada: permite drift silencioso.

### Config + policy separadas

Aceptada: autoridad única por responsabilidad.

## Consecuencias

- Cambiar metadata no altera implícitamente el cálculo.
- Una policy puede reutilizarse de forma explícita entre secciones y quedar congelada en
  cada Publication Snapshot.
- Los scripts actuales requieren una migración compatible desde `config.json` versión 1.
- El schema de `access` no contiene credenciales ni secretos; solo política/configuración.
